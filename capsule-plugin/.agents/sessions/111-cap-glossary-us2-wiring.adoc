== Décisions architecturales (US-2)

. *Wiring mirror `scenarioFile` CAP-SPD-3* — tous les sites étendus
  suivent le pattern `scenarioFile` à l'identique : `ContextConfig` 3ème
  champ `String? = null`, `mergeStr` dans `mergeContextConfig`,
  `CapsuleExtension.glossaryFile: Property<String>` convention `""`,
  `pushConfigIntoExtension` guard `isPresent || blank`,
  `ConfigurableFileCollection @InputFiles @Optional`, lazy provider
  `project.provider { extension > CLI }`, `resolveGlossarySection(budget)`
  5% budget pattern `resolveScenarioSection`. Aucune innovation
  architecturale — pure application du pattern établi.

. *Provenance tracking GLOSSARY* — `trackSources` étendu après SCENARIO :
  `glossaryFile.files.firstOrNull()` → 1 `ProvenanceSource(fileName =
  target.name, chars = readText().length, tokens =
  ContextChannel.estimateTokens(readText()))` si existe. Le
  `ProvenanceTracker.retainOnly` étendu `+= GLOSSARY_CHANNEL` est déjà
  en place côté builder (US-1 S-110). Le log `CAPSULE PROVENANCE →`
  reflète automatiquement le nouveau channel GLOSSARY via
  `tracker.build().channels.size`.

. *Budget 5% pattern `scenarioSection`* — `(budget.totalTokenBudget *
  0.05).toInt().coerceAtLeast(50)` = 400 tokens/8000. Le glossaire est
  un payload terminologique léger, pas un corpus (décision US-0 S-109).

. *Économie d'encre* — `glossaryFile` est `@InputFiles @PathSensitive
  (RELATIVE) @Optional`, le task est UP-TO-DATE quand
  `augmented-context.txt` l'est (même task, mêmes inputs —
  `provenanceFile` aussi). Pas de probe (le glossaire est calculé
  pendant le build, pas re-probé après).

. *Backward compat strict* — `glossaryFile = null` (défaut) →
  `resolveGlossarySection` retourne `""` → `CapsuleContextBuilder.build
  (glossarySection = "")` → tests existants inchangés. Aucun appelant
  existant cassé.
