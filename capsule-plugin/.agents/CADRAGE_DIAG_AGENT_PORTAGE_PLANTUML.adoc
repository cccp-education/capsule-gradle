== 0. Objet & méthode

=== Objet

Le borough PlantUML (HTOWN, `foundry/public/plantuml-gradle`) génère, valide et
traduit des diagrammes PlantUML via LLM (`DiagramProcessor` + `LlmService` +
`PlantumlService` + RAG). `diag-agent` (docToolchain, MIT, ~107 commits) est un
agent LLM de génération de diagrammes d'architecture dont le cœur est une
**boucle d'auto-validation** (génération → validation → raffinement), étendue par
une **validation de description** en amont et un **retour design par vision** en
aval. Ce cadrage recense ce qui est réutilisable, ce qui l'est déjà, et ce qu'il
ne faut **pas** porter.

=== Méthode

== 2. Code review — forces (ce qui a de la valeur)

. **Boucle d'auto-validation ancrée sur un oracle de rendu.** `Orchestrator.execute`
  (`orchestrator.py:347-403`) rend le diagramme via Kroki en SVG ; une erreur de
  rendu (`KrokiRenderError`) est **réinjectée telle quelle** dans le prompt de
  correction suivant (`orchestrator.py:325`). Le verdict est binaire et
  *extérieur* au LLM (le renderer est l'oracle), pas une auto-évaluation textuelle.
. **Pré-vol de description** (`LLMClient.validate_description`, `client.py:148-218`).
  Avant toute génération, un LLM vérifie complétude/cohérence/clarté et renvoie des
  **questions de clarification** plutôt qu'un diagramme dégradé. **Fail-safe** :
  toute erreur → considéré valide (le workflow continue).
. **Retour design par vision** (`client.py:94-146` + `orchestrator.py:359-391`).
  Le diagramme est rendu en PNG, puis **analysé par un modèle vision** qui juge
  mise en page / lisibilité / espacement, et boucle jusqu'à « approved ». C'est le
  seul mécanisme qui capte ce que la validation de syntaxe **ne voit pas**.
. **Budget borné** : double garde `max_iterations` et `max_time_seconds`
  (`orchestrator.py:301-320`), avec `stopped_reason` (`success` / `max_iterations`
  / `max_time`) remonté à l'appelant.
. **Bibliothèque d'exemples few-shot** (`orchestrator.py:159-215`) : exemples
  canoniques par type/sous-type injectés dans le prompt (au-delà du RAG).
. **Détection de sous-type** (`orchestrator.py:129-157`) pour choisir l'exemple et
  le template adaptés (context/container/component ; sequence/activity/class…).
. **Local-first + dégradation** (ADR-003/006) : Kroki Docker par défaut, fallback
  remote en mode auto, mode local strict (erreur propagée).
. **Journal d'exécution** `generation.log` par run (audit du prompt réel envoyé).

[cols="1,2,7,1", options="header"]
|===
| # | Sévérité | Constat | Réf.

| C-1 | 🔴 | **`sys.exit(1)` dans une classe d'orchestration** (`orchestrator.execute`) — couplage bibliothèque↔CLI. | C-2 | 🔴 | **Messages utilisateur allemands codés en dur** dans la couche d'orchestration (`"Die Beschreibung enthält Unklarheiten"`, `"Bitte rufe das Tool…"`) — i18n violée, présentation dans le domaine. | `orchestrator.py:279-282`
| C-3 | 🟠 | **Pas de port/adapter** : `Orchestrator` instancie `LLMClient`/`KrokiClient` en dur ; `litellm.completion` et `httpx.post` sont appelés statiquement → **pas de seam d'injection**, difficilement testable, couplage fort au réseau. | `orchestrator.py:36-40`, `client.py:71`

| C-5 | 🟠 | **Sémantique d'itération incohérente** : boucle test-mode `while (iterations < maxIterations)` vs boucle réelle `while(true)` + `break if (iterations > maxIterations)` → nombre total d'essais divergent (off-by-one) entre les deux chemins. | `orchestrator.py:130` vs `:188`
| C-6 | 🟠 | **Erreur PNG confondue avec « format non supporté »** : toute `KrokiRenderError` sur le rendu PNG est interprétée comme « ce type ne supporte pas PNG » → la validation design est silencieusement **sautée** et le diagramme accepté, même si l'échec était transitoire (réseau). | `orchestrator.py:386-391`
| C-7 | 🟠 | **Collision de noms de sortie** : toutes les sorties sont `diagram.<ext>` (`diagram.puml`, `diagram.svg`, `diagram.png`) → deux runs dans le même `--output` **s'écrasent**. Idem `generation.log` ouvert en `mode='w'`. | `orchestrator.py:422,431,112`

| C-9 | 🟡 | **Race de logger** : `_setup_file_logger` fait `logger.handlers = []` sur `logging.getLogger(__name__)` (logger **module global**) → non thread-safe, en contradiction avec l'ADR-002 (« parallel processing possible »). | `orchestrator.py:108-116`
| C-10 | 🟡 | **Extraction markdown fragile** : regex `` ^```[\w]*\n(.*?)\n```$ `` — exige un `\n` avant la clôture, le tag de langage ne tolère pas `-`/`+` (`c4-plantuml`), pas de gestion des fences non fermées. | `client.py:45`
| C-11 | 🟡 | **Pas de garde de convergence** du feedback design : rien ne détecte que le LLM répète le même retour → consommation d'appels LLM+vision jusqu'à épuisement de `max_iterations`. | `orchestrator.py:379-385`
| C-12 | 🟡 | **Archive non bornée** : un JSON `attempt-history-<timestamp>.json` par run dans le dossier de sortie, sans rotation/cleanup. | `orchestrator.py:301-310`
| C-13 | ⚪ | **Code mort** : 4 modules vides (`analyzer.py`, `validator.py`, `prompt_builder.py`, `limiter.py`) + **1 test vide** (`tests/integration/test_feedback_loop.py`, 0 ligne) — reliquat de refactor. Le « test de la boucle de feedback » est un **test fantôme**. | `tests/integration/`
| C-14 | ⚪ | **Config mono-source** : `Settings` lit uniquement les variables d'env ; `max_iterations`/`validate_design` n'ont pas de flag CLI alors que la doc les présente. Pas de précédence YAML/CLI. | `config/settings.py:39-65`
| C-15 | ⚪ | **Cycle de vie Docker silencieux** : `stop()` avec `check=False` (échecs avalés), `is_running` filtre `docker ps` par sous-chaîne (`kroki` matche `kroki-foo`). | `kroki/manager.py:88-123`
|===

=== Ce qu'il ne faut PAS porter

* `sys.exit` dans une couche non-CLI (C-1) — HTOWN est un **plugin Gradle** ;
  l'échec doit lever `GradleException`, jamais terminer la JVM.
* Messages hardcodés (C-2) — HTOWN a déjà `PlantumlMessages` i18n (10 langues).
* Écriture de sortie `diagram.<ext>` (C-7) — HTOWN **dérive déjà** le nom du
  prompt (`promptFile.nameWithoutExtension`).
* Logger module global muté (C-9) — préférer un logger de tâche Gradle.
* Kroki comme **oracle de validation** — HTOWN valide **nativement** et hors-ligne
  via `net.sourceforge.plantuml.SourceStringReader` (`PlantumlService.validateSyntax`),
  plus rapide et sans Docker.

== 7. Décisions d'architecture

. **Cible = HTOWN (plantuml-gradle), pas capsule.** Ce cadrage est hébergé dans
  Détroit (borough de la session, comme le précédent `CADRAGE_EPIC_LLM_RESILIENCE_N0.adoc`)
  mais l'EPIC et le code appartiennent à HTOWN. **Transfert à acter** (§ 10).
. **Domaine `plantuml.agent` (nouveau, N2).** Objets purs d'abord (parsables,
  hors I/O, unit-testables), ports/adapter ensuite. Aucune dépendance réseau dans
  le domaine.
. **La boucle reste dans `DiagramProcessor`.** On **étend** la boucle existante
  (déjà correcte et couverte) plutôt que d'en écrire une seconde (anti-pattern
  C-5 de `diag-agent`).
. **Aucun nouveau moteur de rendu.** La validation reste **native** (offline) ;
  Kroki n'est **pas** porté (il n'apporte que le multi-format, déjà couvert par
  asciidoctor-diagram).
. **Vision = opt-in et dégradable.** Un modèle sans capacité vision → revue
  **sautée**, jamais un échec de build. La revue design ne bloque pas `check`.
. **Réutiliser `LlmService`/`ChatModel`** (port existant) — ne pas réintroduire
  de couplage direct à un provider.
. **4 sources + `pushConfigIntoExtension`** pour chaque option (`maxSeconds`,
  `designValidation`, `preflight`), défaut `false`/`0` (backward compat).
. **i18n** : toute chaîne utilisateur via `PlantumlMessages` (10 langues) — pas de
  message hardcodé (leçon C-2).
. **Économie d'Encre** : DIA-07 applique la Loi (ne pas re-brûler un appel
  LLM/vision dont le résultat est identique) ; DIA-01 ne relance la revue design
  que si la source a changé.
. **English only** (code, Gherkin, tests) ; gouvernance `.adoc` en français.
