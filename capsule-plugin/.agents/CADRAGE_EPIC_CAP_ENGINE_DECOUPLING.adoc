== Objectif

Découpler le **métier** vidéo du **moteur** reveal.js/slider dans capsule, isoler
un **noyau engine-agnostique** (`capsule.kernel`), poser les **ports neutres**, et
**préparer la mutualisation** du code avec `hyperframes-gradle` (2ᵉ moteur).

Objectif stratégique : faire de capsule un **moteur de production vidéo** dont le
moteur de rendu visuel (reveal.js) n'est qu'un **adaptateur** — afin qu'hyperframes
puisse devenir un **2ᵉ adaptateur** du même noyau (asymétrie d'outillage constatée :
capsule 190 fichiers / 31 tâches, hyperframes 16 fichiers / 3 tâches).

_Origine_ : session pilote 2026-10-12 — demande explicite : « refactoriser capsule
pour découpler le plus possible le métier du moteur et préparer la mutualisation de
code entre les deux boroughs » ; « je ne veux pas attendre 3 boroughs pour l'extraction ».

== Constats (audit au code)

=== C1 — Point chaud : `CapsuleVideoTask.kt` (1248 lignes)

Le fichier mélange deux responsabilités dans le même corps :

* **Noyau** : TTS, audio-post, sous-titres, conversion de format, validation durée,
  injection audio, planification de la capture.
* **Adapter reveal.js** : injection du script d'autoplay `.reveal .slides section[data-audio]`,
  capture Playwright par slide, `createSingleSlideHtml()`, `HtmlSectionParser`,
  `ManimSlideReplacer`, résolution de la stratégie de capture (Playwright/Screenshot/Remotion).

C'est **la** couture à déplacer : le noyau ne doit connaître ni `.reveal`, ni
`<section>`, ni `data-audio`, ni Playwright.

== Décisions

. **D1 — Modèle neutre.** Généraliser `SlideSegment` → `VideoSegment` (index, titre,
   narration, `kind` {`VISUAL`, `ANIMATION`}, `scene?`), `CapsuleScript` → `VideoScript`,
   `CapsuleVideoEntry` → `VideoProductionEntry` (`VisualSource` abstrait, plus `deckFile`).
   **Additif** : `typealias` de compatibilité, zéro rupture 0.0.10.
. **D2 — Deux ports structurants.**
   * `SegmentSource` : `source → List<VideoSegment>` — impl. reveal.js (speaker notes).
   * `VideoEngine` : `render(visual, segments, audio, output)` — impl. `RevealJsEngineAdapter`
     (Playwright) aujourd'hui ; impl. HyperFrames plus tard.
. **D3 — Package `capsule.kernel`.** Noyau isolé, **zéro import** Playwright/reveal/slider/
   `org.gradle` métier. Frontière **gardée par test d'architecture** (pattern
   `bakery` `I18nClientNoDirectHttpBoundaryTest`).
. **D4 — Package `capsule.adapter.revealjs`.** `PlaywrightManager`, `HtmlSectionParser`,
   `ManimSlideReplacer`, `createSingleSlideHtml`, parser speaker-notes, contrat `-script.txt`.
. **D5 — Cible d'extraction : N1 `education.cccp:video-kernel`.** Lib **utilitaire**, pas
   N0 (doctrine S-162 `LLM-RESILIENCE N0` CADUQUE : N0 = contrats purs). Les **ports**
   peuvent devenir un N0 `video-contracts` *si* contractuels. **Extraction effective =
   US ultérieure, accord pilote** — le pilote acte le principe dès maintenant (pas d'attente
   du seuil « factoriser à 2 » — amendement pilote S-195 : un second cas suffit).
. **D6 — Baby-step, additif, backward-compat.** Ne pas casser un plugin mature
   (917 unit + 60 functional + 22 runners Cucumber).
. **D7 — Vocabulaire neutralisé dans le noyau** : ni `slide`, ni `deck`, ni `reveal`,
   ni `Playwright`. Le noyau parle `segment`, `visual`, `engine`.

== Risques

* **Régression** sur plugin mature (0.0.10, CI verte). Mitigation : additif (`typealias`),
  frontière testée, baby-step DDD/TDD/BDD, Local = Build / Tests = CI.
* **Sur-abstraction** : créer des ports pour 2 consommateurs (capsule + hyperframes).
  Mitigation : le pilote acte explicitement l'extraction anticipée ; les ports restent
  **minces** (`SegmentSource` + `VideoEngine`), pas de générique paramétré par 5 callbacks.
* **Nommage du module partagé** (N1 `video-kernel`) à trancher en US-5.
